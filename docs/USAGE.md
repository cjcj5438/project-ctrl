# project-ctrl 使用说明

一台 Mac 上的项目管家：把散落在各处的仓库收进来、打 tag 归类、看 README，
以及 —— 从 v0.4.0 起 —— **管理每个项目的多个服务、用仓库内的声明文件固化配置、
编排 docker compose、避开端口冲突**。

> 截图来自 `docs/images/`，都是真实的界面（不是示意图）。
> 界面从 v0.4.0 起使用语义化设计 token 与 SVG 图标，并支持亮/暗双套主题；
> 截图取自深色主题，与系统外观一致时看起来会和文中一致。

## 1. 第一个项目：把目录收进来

打开 App，右上角有三个添加方式：

| 按钮 | 用途 |
|---|---|
| **扫描文件夹…** | 选一个父目录，列出它的一级子目录，勾选后批量加入 |
| **添加单个项目…** | 把选中的目录**本身**作为一个项目加入 |
| **从 GitHub 克隆…** | 粘贴仓库地址，克隆完成后自动加入 |

「扫描文件夹…」的行为值得记一下：跳过隐藏目录、**已加入的不再出现**、
候选目录不要求有 `.git`。所以你可以把 `~/my` 整个扫一遍，只勾想要的。

扫描结果是一个对话框：列出该目录下**尚未加入**的一级子目录，可以全选、逐项勾选，
并在「加入」时给这一批打 tag（逗号 / 空格分隔，可留空）。

## 2. 列表页：找得到、分得清

![列表页](images/02-list.png)

每张卡片显示：项目名（就是文件夹名）、完整路径、创建日期、磁盘大小、tag。
卡片标题右侧的小绿点表示**该项目的服务正在运行**；悬停卡片标题可看完整 phase，
读屏会读出「服务运行中」。

顶部那一行：

| 控件 | 说明 |
|---|---|
| 搜索框 | 按名称过滤（不区分大小写） |
| 排序 | 创建日期倒序 / 名称 / 大小，点一下换一种（创建日期读目录 birthtime，见第 11 节） |
| 筛选 tag | 多选，**AND 语义**（同时具备所有选中的 tag 才会显示） |
| 批量探测… | 只读扫描所有项目能怎么跑，勾选后只写本机（见第 4 节） |
| 外部服务… | launchd / PM2 的只读视图（见第 10 节） |
| 主题 | 跟随系统 / 浅色 / 深色三档，选择会记住 |

标题下面有两个视图切换：**项目**（默认，卡片网格）与**服务**（运行态表格）。
服务视图不是另一个列表——它只显示「正在跑」和「出问题」的服务，空的时候会说明原因。

### 运维条

只要有服务在运行或异常，项目视图上方会出现一条紧凑状态带：`● api :8080 · ● worker · 1 个异常`。
排序是**异常（崩溃/失败）> 运行中 > 执行中**，同相位按项目 id + 服务名稳定排序；悬停每颗胶囊可看
`项目 / 服务（状态 · 端口）`。没有活跃服务时这条不出现——不做空装饰。

tag 分两种，视觉上就能区别：

- **蓝底实心**（`primary`）— 你手动打的，可改可删；筛选栏选中态同色
- **虚线边框** — 自动算出来的只读 tag：`git`（有 `.git`，文件或目录都算）、`无git`（没有 `.git`）、
  `github`（仅 `.git` 为目录且任一 remote 指向 github.com 时才有；linked worktree/submodule 的 `.git` 是文件，永不标 `github`）

> 自动 tag 不入库、不可手改，但**可以用于筛选**。所以「只看有 git 的项目」就是点一下 `git`。

## 3. 详情页：一个项目的全部操作

点任意卡片进入。

![详情页](images/05-source.png)

从上往下：

1. **基本信息** — 路径、创建日期、磁盘占用
2. **tag** — 输入框回车即可添加，点 tag 上的 `×` 删除
3. **快捷按钮** — Finder / iTerm / VS Code / GitHub（识别到 GitHub remote 时出现）
4. **从管理器移除** — 只删记录，**不动任何文件**
5. **源码**（折叠面板）— 见第 9 节
6. **服务**（折叠面板）— 见第 4 节
7. **README** — 渲染 / 编辑 / 生成

### README

- 默认渲染 Markdown（`marked` 转 HTML 后经 DOMPurify 清洗；相对路径图片以内联 data URL 显示，加载失败显示占位）
- 点「编辑」进入左编辑右预览的编辑器，`Cmd+S` 保存
- 编辑期间如果文件被外部改动，会提示冲突（可覆盖保存或放弃重载），**不会静默覆盖**
- 没有 README（`README.md`/`readme.md` 都不存在）时点「生成」按模板创建 `README.md`

### 路径丢失

目录被删 / 改名 / 移动后，卡片会显示「路径丢失」，详情页提供「重新关联」（重新选目录）
与「移除」。记录不会自动消失——免得你误删了磁盘挂载或移动硬盘时丢掉 tag。

## 4. 多服务：一个项目可以跑好几个

一个项目现在可以有**任意多个服务**，每个服务是「有序的一次性步骤 + 一个长驻命令」：

```
api      run: pnpm dev         steps: install, migrate     ports.listen: 8080
worker   run: pnpm worker      steps: —                    无端口
db       docker: infra/docker-compose.yml up -d postgres     ports.requires: 5432
```

展开详情页的「服务」，每个服务是一行（点开才有按钮与日志）：

![服务面板与探测候选](images/04-service-running.png)

| 元素 | 含义 |
|---|---|
| 圆点 + 状态 | 未运行 / 执行中 / 运行中 / 已停止 / 已崩溃 / 失败 |
| `:8080` | **实际**监听的端口（spawn 后实测，不是猜的） |
| `重启 N 次` | 崩溃后被自动拉起的次数 |
| `.json` / `db` | 这条声明来自仓库内 `.project-ctrl.json`，还是本机数据库 |
| 黄色提示 | 「已改用 8082（8080 被 com.docker.backend 占用）」「沿用上次的端口 8081（期望 8080）」这类解释 |

每个服务自己的按钮：`启动`（预检未返回前显示「预检中…」并禁用）`停止` `重启` `打开` `install` `build`（步骤名就是按钮名）
`编辑` `刷新`；docker 服务还有 `compose up` / `compose down`。
面板底部有 `添加服务…`、`全部停止` 与 `刷新`；本机栏可设端口偏移与「退出后保留进程」。

### 步骤不会自动执行

`steps` 是**独立按钮**，点一下跑一次。`启动` 只跑 `run`，不会顺带安装依赖——
这样「点启动」永远是快的、可预期的。想一键准备，就在 `run` 里显式写
`["/bin/zsh","-lc","pnpm install && pnpm dev"]`（见第 5 节的 shell 规则）。

步骤失败（含超时）会进「失败」（即使退出码是 0 也一样——步骤的语义是"跑完即结束"，没有"成功常驻"），**不会**被自动重启——一次性任务重跑可能破坏数据。

### 依赖顺序

服务可以声明 `depends_on`。启动某个服务时，它依赖的服务按拓扑顺序**先起**，
并等有端口的依赖最多 30 秒就绪（`wait_ready` 端口探测；超时只记一条提示，不阻塞）。循环依赖或指向不存在的服务会在启动前报错。

### 崩溃自愈

`restart` 三档：`never` / `on-failure`（默认）/ `always`。崩溃（非零退出）后按指数退避重试
（0.5s → 1s → 2s … 封顶 30s），连续失败 5 次就停下并写明「已连续重启 5 次仍失败，停止自动重启」。
正常退出（码 0）进「已停止」不重启；手动 `停止` 会取消待执行的重启。

### 快速关联：三条路径

没有声明时，面板会列出探测结果：`package.json` 的 `dev`/`start`/`serve`（按此顺序取首个命中的脚本；
另有 `install` 与 `build` 进步骤候选）、`docker compose` 里能作为栈启动的服务（顶层与一层子目录如
`infra/`，含 `docker-compose.*.yml` 兄弟 override 叠加）、`Makefile` 目标（行首目标名）、
根目录/ `bin/` / `scripts/` 下的启动脚本（根目录只收 `start*`/`serve*`）。

| 动作 | 写哪里 | 会不会让仓库变脏 |
|---|---|---|
| 点「保存」 | `~/.project-ctrl/data.db` | 不会 |
| 「固化为仓库声明…」 | 项目根的 `.project-ctrl.json` | **会**（你主动点的，且已有文件不会被覆盖） |
| 手工编辑 `.project-ctrl.json` | 仓库 | 会 |

还有一种更轻的：**临时运行**（后端 `run_adhoc` 命令：不写库也不写文件，直接起一个进程试试；
关掉 App 就消失，不会留下你从未确认过的配置）。当前版本前端尚未接入口，如需试用请走 IPC 直接调用。

### 批量探测

工具栏「批量探测…」只读扫描所有项目，列出每个项目能怎么跑。勾选后点「采纳到本机」，
**只写本机数据库**：批量操作不该让几十个仓库同时变脏。已有 `.project-ctrl.json` 的项目
不会被写入（文件才是真相源），后端也会拒绝；子目录里的 compose 栈（路径含 `/`）不在批量里出现，
请到单个项目的服务面板里点选。

## 5. `.project-ctrl.json`：把配置写进仓库

把声明放进项目根，就能提交、能分享、能换机器。文件名固定，不许嵌套。

```json
{
  "schema_version": 1,
  "services": [
    {
      "name": "api",
      "cwd": "frontend",
      "run": ["pnpm", "dev"],
      "steps": [
        { "name": "install", "argv": ["pnpm", "install"], "timeout_s": 1800 },
        { "name": "migrate", "argv": ["pnpm", "db:migrate"], "timeout_s": 600 }
      ],
      "env_files": [".env.development.local"],
      "env": { "NODE_ENV": "development" },
      "ports": { "listen": 8080, "requires": [5432] },
      "health": { "type": "http", "path": "/healthz", "timeout_ms": 30000 },
      "depends_on": ["db"],
      "restart": "on-failure"
    },
    {
      "name": "db",
      "docker": {
        "files": ["infra/docker-compose.yml", "docker-compose.override.yml"],
        "services": ["postgres", "minio"]
      }
    }
  ]
}
```

### 字段全是可选的，除了 `name`

| 字段 | 说明 |
|---|---|
| `cwd` | 相对项目根的工作目录（monorepo 子包），不许绝对路径、不许 `..`、不许空 |
| `run` | 长驻命令。省略表示这是个「只有步骤」的服务 |
| `steps[]` | 一次性步骤：`name` + `argv` + `timeout_s`（默认 1800） |
| `env_files[]` | 相对项目根的 env 文件，只记文件名，值留在文件里；本机层也可追加同名字段 |
| `env` | 直接声明的变量；优先级高于 `env_files`；**注意：固化时会把这里的值（含 secret）写进仓库文件，提交前请检查** |
| `ports.listen` | 自己要监听的端口（被占则顺延） |
| `ports.requires` | 必须已在监听的依赖端口（不阻塞启动，只提示） |
| `health` | `{type:"port"}`（默认）或 `{type:"http", path:"/healthz"}`，`timeout_ms` 缺省 30s；用于判定「就绪」，超时只记提示不杀进程 |
| `depends_on[]` | 先启动的服务名 |
| `restart` | `never` / `on-failure`（默认）/ `always` |
| `docker` | 见第 6 节 |

### 校验是严格的，故意如此

未知字段**直接报错**，错误信息会点名那个键：

```
描述文件解析失败：unknown field `enviroment`, expected one of `name`, `cwd`, `run`, …（未知字段会直接报错，请检查拼写）
```

理由是：在几十个仓库里放文件，静默忽略拼错的键会让你遇到「服务跑起来了，但 env 没生效」，
而你不会知道。`schema_version` 比 App 支持的更新时，整个文件拒绝读取并说明原因。

文件坏了的时候，服务面板顶部会显示红色错误条与原文，**不会**回落到数据库里的旧配方——
否则你改了文件却还在跑旧命令，这是最难排查的一类问题。

### 三层覆盖

| 层 | 文件 | 谁写 | 内容 |
|---|---|---|---|
| 声明 | `<项目>/.project-ctrl.json` | 你 / 团队 | 可提交的共享配置 |
| 本机 | `~/.project-ctrl/overrides.json` | 只有你（含 UI 里的「本机」栏） | 端口偏移、`keep_alive`、`restart` 覆盖、额外 env 与 env_files |
| 观测 | `~/.project-ctrl/state/ports.json` | App 自动 | 上次实际分配到的端口 |

合并顺序是「声明 → 本机 → 观测」。本机层里**认不出的键原样保留**（与仓库声明的严格校验
方向相反），所以你可以手写注释性字段，App 不会抹掉它们。注意本机层是「只增不删」的合并：
一旦写过 `port_offset`，即使 UI 里改回 0 也要显式保存才会清除旧值。

### shell 的规矩

命令一律是 argv 数组，App 永不替你拼 shell 字符串。需要管道、`&&`、变量展开时，
显式写成 `["/bin/zsh","-lc","…"]` —— 让「看到的就是执行的」成立。

## 6. docker compose 编排

一个 `docker` 引用 = 一个服务，可以叠加多个 `-f`：

- `compose up -d <services...>` 启动（`services` 为空时整栈启动）
- `ps --format json --all` 读容器状态（含已停止容器），按服务名过滤后列在面板里（只读子行）；
  daemon 没起 / 命令失败时面板显示错误 + 重试，不再显示"没有容器"
- `logs -f --tail 2000 --no-color` 跟随日志，输出直接进**与服务相同的日志面板**（不需要第二套通道）；
  收起卡片即停止跟随（容器本身不受影响），退出 App 时全部停掉
- 没有声明子服务时 `compose down` 整栈停止；声明了子服务时退化为 `stop <services...>`（`down` 不接受服务名）

**不做**容器级接管：profiles、extends、env 插值这些语义让 docker 自己负责，
我们只读它的 JSON 状态。这样 compose 文件怎么改都不会和 App 里的记录打架。

## 7. 端口冲突是怎么解决的

这是这个工具最想解决的问题。分四步，每步都有人读得懂的理由。

### 第一步：判定"被占用"要比 bind 更严

在 macOS 上，别的进程只在 IPv6 `*:8080` 上监听时，你**仍然能** bind `127.0.0.1:8080`。
只看 bind 会把已被占用的端口判成空闲。所以除了 bind，还查一次 `lsof -nP -iTCP -sTCP:LISTEN`（只看 TCP，UDP 端口不在判定范围内）。

### 第二步：先试上次用过的端口

`state/ports.json` 里记着这个服务上次实际监听的端口。下次启动先试它——
URL 才不会每次顺延都变一次。

从期望端口开始，最多往后试 9 个（含期望本身共 10 个候选；期望为 0 时直接失败，不分配）。成功了不静默——状态里写着
「已改用 8082（8080 被 com.docker.backend 占用）」。注意候选首位是上次用过的端口：
如果旧端口恰好空闲，即使你改了偏移/期望，仍会沿用旧端口并提示「沿用上次的端口」。

### 第四步：让进程真的听新端口

顺延了但进程还听旧端口，等于没解决。按顺序尝试：

1. 命令行里已有 `--port N` / `-p N`（末尾优先，否则任一处）→ 改掉那个数字
2. 有 `vite.config.{ts,js,mjs,mts}` → 追加 `--port N`（npm/yarn 的 `run/start` 前插 `--` 分隔符）
3. 有 `next.config.{js,mjs,ts}` → 追加 `-p N`（同上插 `--`）
4. 都不命中 → 注入环境变量 `PORT=N`（命令行注入命中时**不再**注入 PORT，避免两处打架）

> **实测结论**：`--port` 重复时**后出现的值生效**，所以追加是安全的。

有 `ports.listen` 的服务，端口计划**始终执行**（即使没顺延也一样）：`node server.js` 这类命令不会自己读端口，
只有 `PORT=N`（或改写后的命令行）能让它听在被分配的端口上。没有 `listen` 的服务不分配端口、不注入。

### 依赖端口不一样

`ports.requires` 里的端口语义是**必须正在监听**（那是你要连的数据库）。没人监听时
只提示「端口 5599 无人监听：先起依赖服务或容器」，**不阻止启动**。

## 8. 退出后保留进程与重新接管

默认行为没变：关掉 App（包括 `Cmd+Q`）会收掉所有受管进程组。

但每个服务的「本机」栏有一个开关：**退出后保留进程**。勾上之后：

1. 退出 App 时这个服务**不杀**，凭据在 `~/.project-ctrl/state/run/` 下记下
   `key / pid / pgid / argv / cwd / started_at / port / keep_alive`（文件名是 key 的安全化形式，
   非字母数字的字符会被替换，不是 `<key>.json` 原样）；
2. 下次打开 App，启动时逐条校验**三项**：进程还活着、`ps -o lstart` 与记录的启动时间相符、
   `ps -o command` 与记录的 argv 按词相符（脚本服务会归一化解释器行再比）；
3. 三项都过才**接管**（面板直接显示「运行中」），任一项不过就丢弃这条记录。

为什么校验这么严：PID 会被系统复用，只凭 `kill -0` 判活可能把别人的进程当自己的，
而停止是对整个进程组发信号——那会误杀无关进程。

> 保留决定在**退出这一刻**重新读取，所以服务启动之后再勾开关也有效。

**崩溃或强杀怎么办**：凭据在 `spawn` 的同时就落盘了。如果 App 被 `kill -9` 或崩溃，
下次启动会发现这些「不是你要保留」的凭据，于是**回收**（杀掉）这些孤儿进程并清理记录，
而不是接管它们。不会留下占端口的游离进程。

## 9. 更新源码：源码面板

![源码面板](images/05-source.png)

显示：分支（detached HEAD 会明确标出）、upstream、未提交改动数、落后几个提交、领先几个提交。
「不是 git 仓库」时面板直接说明，不显示按钮。

| 按钮 | 行为 | 何时可用 |
|---|---|---|
| **检查更新（fetch）** | `git fetch --prune --no-tags` | 是 git 仓库即可 |
| **拉取（pull --ff-only）** | `git pull --ff-only` | 需同时满足下面 6 条 |

`pull` 的前置条件按顺序判定（缺一条按钮就灰，并写明是哪一条）：

1. 是 git 仓库
2. 不是 detached HEAD（提示「需先 checkout 分支」）
3. 有 upstream
4. 工作区干净（0 个未提交改动）
5. 没有未推送的提交
6. 确实落后（否则「已是最新」）

**没有**一键 `reset --hard`，**没有**自动 `stash`。脏工作区时只能 fetch 看落后数，
然后去 iTerm 自己处理——因为自动 stash/pop 在冲突时会留下半坏状态，比直接拒绝更糟。

## 10. 从 GitHub 克隆与导入 PM2

工具栏「从 GitHub 克隆…」→ 粘贴地址（`https://` / `http://` / `ssh://` / `git@` 开头才允许，`file://` 等一律拒绝）→ 选父目录 → 克隆。

- 目录名从仓库地址最后一段推断（去掉 `.git` 与末尾 `/`）
- 父目录必须已存在；目标已存在时**报错不覆盖**
- 克隆完成后自动加入管理器

---

### 导入已有的 PM2 配置

后端 `import_pm2` 命令会读 `~/my/PM2/ecosystem.config.js`（固定路径，不可配），把里面的应用转成项目 + 配方。
当前版本工具栏尚未接入该命令，文档先记行为：

| 情况 | 结果 |
|---|---|
| 目录存在、无配方 | 新增项目并写入配方（来源标 `pm2`，`env` 全量入库、`PORT` 数字进 `listen`） |
| 已有配方 | 跳过，不覆盖你的修改 |
| 目录不存在 | 记入 errors 并列出（例如已删除的项目） |
| 文件不存在 | 不报错：errors 里记一条「未找到」，返回空报告 |

**只读**那个配置文件，不修改它，也不删除任何东西。

### 外部服务视图（只读）

工具栏「外部服务…」把两处**已安装**的守护配置列出来：`~/Library/LaunchAgents/*.plist`
（文本解析，只读 Label / ProgramArguments / WorkingDirectory；二进制 plist 会被跳过）
与 PM2 的 `ecosystem.config.js`（按 `~/my/PM2/` → `~/PM2/` → `~/` 顺序取首个存在的文件；没有 node 时读不出）。

| 列 | 含义 |
|---|---|
| 来源 | `launchd` / `pm2` |
| 名称 | plist 的 Label / PM2 的 app name |
| 目录 | `WorkingDirectory` / `cwd` |
| 说明 | launchd：`KeepAlive` 标记 + 可执行文件路径（或「已安装」）；PM2：「配置存在 / 工作目录不存在」 |
| 状态 | `已声明`（同名服务的命令与外部**完全一致**才算） / `已管理项目`（目录已在库中但名不对或命令不同） / `无关`（目录不在库中） |

每次打开都会**重新读文件**，不缓存——你手工改过 plist 之后，
面板必须跟着变（当前版本没有「重新读取」按钮，关掉重开即可）。漂移检测（`command-mismatch`）
只做比较与展示，**不会**去改 plist、也不会调 `pm2 start`：
那会和它们自己的保活策略抢同一个进程。

## 11. 数据、边界与已知限制

### 数据位置

```
~/.project-ctrl/
  data.db              # projects / tags / project_tags / services
  overrides.json       # 本机层（你写的）
  state/ports.json     # 上次实际端口（App 写的）
  state/run/<safe-key>.json # 收养凭据（App 写的；safe-key 是 key 的安全化文件名）
```

`services` 表是「每项目多行」，`UNIQUE(project_id, name)`。schema 版本记在
`PRAGMA user_version`，启动时按顺序迁移——**不会删库**。

**从 v0.2.0 升级**：旧的单配方会被自动转成新模型，`install`/`build` 变成两个步骤（`timeout_s` 都取默认 1800）、
`start` 变成 `run`、`dev_port`/`requires_ports` 变成 `ports`，`env`/`node_pin`/`toolchain`/`origin` 原样带过去，一条都不丢。
新服务名固定叫 `default`。

环境变量 `PROJECT_CTRL_DATA_DIR` 可以指向别处（测试 / 演示时用，避免污染真实数据）。

### 写入边界

| 它会不会… | 答案 |
|---|---|
| 往项目目录写配置文件？ | 只有你点「固化为仓库声明…」时写 `.project-ctrl.json`；其余情况只写本机数据库 |
| 覆盖已有的 `.project-ctrl.json`？ | **不会**。已存在时拒绝写入（错误里写"已存在；请手工编辑或确认覆盖"）；当前 UI 尚未接入覆盖确认，遇到时请手工编辑文件 |
| 改 launchd plist / 调 `pm2`？ | **不会**。外部服务只做只读展示与漂移比对 |
| 批量采纳会写仓库文件吗？ | **不会**，只写本机数据库 |
| 写 README？ | 会（生成 / 保存按钮，你主动点的） |
| 跑 `git fetch` / `pull --ff-only` / `clone`？ | 会，但都是你点的按钮，且 `pull` 有前置条件 |
| 跑 `reset --hard` / `stash` / `checkout` / `push`？ | **不会**，永远不会（详情页 git 按钮只有 `status`/`log` 白名单） |
| 继承你的 shell 环境给服务进程？ | **不会**，从零构造（只给 `PATH`/`HOME`/`TERM`/`LANG`/`NO_COLOR`/`GIT_TERMINAL_PROMPT` + 声明的变量；`.zshrc` 不读） |
| 自动安装工具链（go / node 等）？ | **不会**。缺什么就显示缺什么 |

### 已知限制

- 项目里**硬编码**的端口（例如 `VITE_VIEWER_URL=http://127.0.0.1:5173`）不会被改写：
  端口注入只认 `--port/-p` 参数与 vite/next 配置文件，其它位置的数字一律不动。
  顺延后请自己改项目配置，或给服务指定不会被占的固定端口
- node 版本只从 `.nvmrc` / `engines.node` 里取**精确的 `X.Y.Z`**（如 `^22.18.0` 取 `22.18.0`）；
  `>=23` 这类取不出精确版本的只提示不猜；`.nvmrc` 优先于 `engines`
- 运行状态本身只在内存里；只有勾了「退出后保留进程」（`keep_alive`）的服务会在重启后被接管（见第 8 节）
- 有 `services` 的 compose 服务按 `stop <services>` 停止（容器保留，可 `up` 恢复）；无 `services` 的整栈 `down`
- 容器不提升为独立服务：compose 里的子容器只能随栈启停，或在面板里只读查看（含已停止容器）
- 创建日期读目录 birthtime（`YYYY-MM-DD`，本机时区），目录被拷贝 / 备份恢复后会变；读不到时显示"未知"
- `.git` 为文件时（linked worktree / submodule）只标 `git`，不做 GitHub 识别；`status`/`log` 照常可用
- UDP 端口不在占用判定范围内；`listen: 0` 会直接启动失败（不会分配随机端口）

## 12. 常见问题

**Q：启动后状态是「已崩溃」，日志里说 `command not found`？**
配方指向的命令在这台机器上不存在，或该项目的依赖没装。点该步骤按钮（如 `install`）先装依赖，或点「编辑」改配方里的命令。
（预检会在展开卡片时提前标出缺失的可执行文件，启动按钮也会置灰。）

**Q：端口被顺延了，但页面里的接口请求全挂了？**
项目里硬编码了旧端口（例如前端配的 proxy target 或 `VITE_*` URL）。状态里的黄色提示（「已改用 N…」）就是在说这件事——
改项目配置，或者给它指定一个不会被占的固定端口。

**Q：为什么「拉取」按钮一直是灰的？**
看它旁边那行字，会写明原因：`不是 git 仓库` / `detached HEAD，需先 checkout 分支` / `没有 upstream` /
`工作区有 N 个未提交改动` / `有 N 个提交未推送` / `已是最新`。前三种需要你在终端里处理（建仓库/切分支/设 upstream），
后两种先提交或推送。

**Q：启动按钮灰，提示「缺少可执行文件：go」？**
本机没装 go（或该项目的 `Makefile`/子目录 `go.mod` 需要它）。这类工具链缺失不会被自动安装（会污染你的环境），按提示自己装。

**Q：关掉 App 后服务还在跑吗？**
默认不会，退出时收掉所有进程组。想让它继续跑，在该服务的「本机」栏勾上「退出后保留进程」，
下次打开会自动接管（见第 8 节）。

**Q：声明会跟着仓库走吗？**
写成 `.project-ctrl.json` 就会（可以 commit）。只点「保存」则存在本机数据库，换机器需要重配
或重新固化。

**Q：我在 `.project-ctrl.json` 里改了命令，为什么面板还是旧行为？**
文件解析失败时面板顶部会有红条。未知字段、拼错的键、`schema_version` 过新都会被拒绝——
看那条错误信息里的字段名即可。

**Q：为什么「启动」没有自动安装依赖？**
`steps` 是独立按钮。`启动` 只跑 `run`，保证点击永远是快的、可预期的。
